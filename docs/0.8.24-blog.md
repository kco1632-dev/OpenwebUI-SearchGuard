# Bonsai2 + Open WebUI Native Web Search を実用化する — SearchGuard 0.8.24 までの検証記録

## はじめに

ローカルLLMの Bonsai2-27B を Open WebUI から利用し、Native Web Search を組み合わせる環境を構築した。

しかし、単に検索機能を有効にするだけでは、実運用上いくつかの問題が発生した。

- 検索を何回続けるかをモデル任せにすると、検索履歴が膨張する
- 検索結果を取得しても、目的と異なるURLを fetch することがある
- fetch の重複や検索結果のノイズが tool-loop を長引かせる
- current/latest 系の質問では、モデルが検索 query に入れる日付が不安定になることがある
- tool limit 到達後に、モデルがもう一度 `<tool_call>` を生成しようとすることがある
- native tool call ではなく、raw `<tool_call>...</tool_call>` が通常の回答テキストとして現れることがある

そこで、Open WebUI の Filter として Bonsai2 用の SearchGuard を段階的に作成した。

本稿では、2026年10月7日時点の **v0.8.24** を一つの安定した観測ベースラインとして、その設計、実測結果、そして「ここから先は簡単には直せない」と判断した理由をまとめる。

---

## 1. 目標は「検索を賢くする」ことではなく「検索を制御する」こと

SearchGuard の基本思想は、モデルそのものを別の検索エージェントに置き換えることではない。

Bonsai2 が Native Web Search を使う際に、

1. 必要なら最初の検索を強制する
2. search / fetch の成功回数を制御する
3. tool-call turn 数を制限する
4. 検索結果が目的の entity を含むか監査する
5. fetch するURLをある程度選別する
6. 重複 fetch を抑える
7. tool limit 到達後は検索を終了して回答フェーズへ移行する
8. 異常な raw tool-call を観測する

という「実行制御層」を設けることである。

これは重要な区別だった。

検索結果の質そのものを Guard が生成するわけではない。

---

## 2. 0.8.x で積み上げたもの

SearchGuard は一度に完成したわけではない。

0.8.19 では、日付文字列が検索対象の主要 entity として誤認される問題を修正した。

例えば、

```
2026/10/5の4755の終値
```

のような質問で、年の「2026」が主要 entity として選ばれると、検索結果監査が本来の銘柄ではなく「2026」を探してしまう。

そこで日付部分を mask して entity 抽出を行うようにした。

0.8.20 では Date Preflight を追加した。

current/latest/today などの相対時間表現がある場合、Guard 自身が現在日時を取得し、モデルに absolute date を伝える。

0.8.21 では、この preflight を日付だけでなく時刻まで拡張した。

0.8.22 では、tool execution limit と final-answer generation を分離した。

つまり、

「検索をこれ以上続けさせない」

ことと、

「だから回答も生成させない」

ことを分離した。

これは実運用上かなり重要だった。

0.8.23 では、この final-answer hop にさらに raw `<tool_call>` 除去処理を追加した。

ただし、通常の検索 hop は変更しない。

そして 0.8.24 は、あえて検索動作を変更せず、raw `<tool_call>` 問題の診断だけを追加した。

---

## 3. 0.8.24 が観測した異常

過去のテストでは、次のような現象が発生した。

```
<tool_call>
<function=search_web>
<parameter=query>
...
</parameter>
</function>
</tool_call>
```

しかし Open WebUI 側では、これが native tool call として認識されず、assistant の通常 content として届いていた。

そこで 0.8.24 では、

```
RAW_TOOL_CALL_DIAG
```

という診断ログを追加した。

例えば実測では、

```
finish=stop
native_calls=[]
xml_in_content=True
xml_in_reasoning=False
final_mode=NO
fetch_suspended=YES
action=OBSERVE_ONLY
```

という状態が記録された。

これは少なくとも、

「Guard が native tool call を受け取ったのに処理を間違えて raw XML に変換した」

という単純な説明とは一致しない。

Guard の観測時点ですでに、native_calls は空で、XML は通常 content に存在していたからである。

ただし、ここから直ちに「Bonsai2 が原因」と断定することもできない。

候補には、

- Bonsai2 / PrismML llama.cpp
- tool-call parser
- Open WebUI の tool-loop
- SearchGuard の state
- それらの組み合わせ

が残っている。

0.8.24 は、この原因を決め打ちしないことを目的としている。

---

## 4. 実際の検索テストで分かったこと

単純な検索ではかなり正常に動作する。

例えば、

- 現在の Apple CEO
- Microsoft の2026年AI発表
- 日本の首相
- 企業の公式ページによる役職確認

などでは、検索 → fetch → 回答という流れが成立した。

一方、条件が増えると弱点が目立つ。

### 4-1. 公式情報を探す検索

Apple CEO のテストでは、Apple公式の John Ternus のページまで到達し、CEOであることを直接確認できた。

これは検索・fetch・証拠確認の成功例である。

### 4-2. Apple / Microsoft AI戦略比較

Microsoftについては、公式の2026年Copilot発表を取得できた。

一方Appleでは、Apple公式の製品ページを取得したものの、それを「2026年AI戦略の重要な動き」として採用してしまった。

後から別検索で確認すると、Appleには2026年6月の Apple Intelligence / Siri AI に関する、より直接的な公式発表が存在した。

つまり、このケースは「検索できなかった」というより、

**検索結果の中から条件に最も合う証拠を選択する能力に問題があった**

と評価するのが適切だった。

### 4-3. 現在の販売価格

MX Master 3S や酒類などの価格調査では、検索結果に価格が表示されても、実際の商品ページを fetch できなければ価格を採用しないという条件を設けた。

これは Guard の思想と相性がよい。

検索スニペットをそのまま「確認済み価格」にしない。

商品ページが取得できなければ、

「確認できない」

と答える。

この挙動は、価格調査における hallucination 防止として有効だった。

### 4-4. 日付条件の厳しいニュース検索

一方、

「2026年10月5日に日本で発表・公開されたAIニュース」

のような条件では難易度が急激に上がる。

検索結果にはニュースサイトのトップページや検索ページが混ざり、fetch も blocked / duplicate / page-not-found などが発生した。

さらに raw `<tool_call>` が再発した。

このようなケースでは、単に検索回数を増やせば解決するとは限らない。

## 5. SearchGuard のカウンタは3種類に分けて考える

検証中に重要だったのが、tool の「回数」を一つの数字として扱わないことだった。

Guard には少なくとも、

- search_attempts
- fetch_attempts
- search_count
- fetch_count
- turns
- hop

がある。

`search_count` と `fetch_count` は成功数である。

tool result がエラーだった場合、その成功 quota は消費しない。

Guard が blocked / duplicate としたものも成功数には入れない。

一方 `turns` は別物である。

native tool_calls を持つ assistant message の数を数えるため、tool 実行がエラーだったとしても、その tool-call turn 自体は turn cap の対象になる。

また `hop` は Guard の request/hop 単位であり、`turns` と同じ意味ではない。

この区別をしないとログを読み違える。

---

## 6. なぜ「簡単には解決できない」と判断したか

ここまでの検証で、検索品質には少なくとも3つの層があることが見えてきた。

### 第1層: 検索基盤

DDGS がどの検索結果を返すか。

ここで目的の一次情報が上位に出なければ、モデルには選択肢がない。

### 第2層: Bonsai2 の検索判断

検索結果が与えられたとして、

- どのURLを fetch するか
- もう一度検索するか
- query をどう修正するか
- 日付条件を満たすか
- 公式一次情報を優先するか

を判断する必要がある。

ここはモデルの能力に強く依存する。

### 第3層: Web Loader / fetch

モデルが正しいURLを選んでも、

- JavaScript challenge
- anti-bot
- ページ移転
- robots / access restriction
- 検索結果ページそのもの

などによって取得できないことがある。

今回の富士通のテストでは、正しい公式ドメインを検索で発見できたにもかかわらず、fetch が Vercel Security Checkpoint に阻まれた。

これはモデルの検索能力だけでは解決できない。

---

## 7. SearchGuard 0.8.24 の現在位置

0.8.24 は完成版というより、

**「これ以上コードをいじる前に、現象を観測できる状態にした版」**

と位置付けるのが正確である。

現時点で確認できていることは、

- Native Web Search は正常に動くケースがある
- 公式一次情報を直接確認できるケースもある
- 検索結果の選択に失敗するケースがある
- 複雑な調査では fetch が不安定になり得る
- fetch 側のサイト制限もある
- raw `<tool_call>` が native_calls なしの通常 content として到達するケースがある
- 0.8.24 はその状態を診断ログとして記録できる

というところまでである。

逆に、まだ証明できていないこともある。

- raw `<tool_call>` の根本原因
- DDGS と Bonsai2 のどちらが何％検索品質を決めているか
- context length がどの程度検索品質を低下させるか
- fetch failure が raw XML を直接誘発しているか
- Open WebUI の tool-loop と Bonsai2 のどちらが同期問題の主因か

これらは今後、ログを増やして切り分ける必要がある。

---

## 8. 今後の方針

当面は **0.8.24を固定して観測する**。

特に、

1. 単純な公式一次情報検索
2. 複数テーマ検索
3. 日付制約付きニュース検索
4. 商品価格調査
5. fetch failure
6. raw `<tool_call>` 再発

を分けて記録する。

そして、検索結果を

「検索エンジンが悪い」

「モデルが悪い」

「Guardが悪い」

と一括りにしない。

必要になった段階で、

- DDGS の固定条件テスト
- 同一SERPに対するモデルのURL選択テスト
- fetch 成否の監査
- 別モデルとの比較
- prompt / context サイズの比較

を行えば、かなり正確に層別化できる。

---

## まとめ

Bonsai2-27B に Open WebUI Native Web Search を組み合わせると、ローカルLLMでも実用的なWeb検索環境を構築できる。

ただし、「検索できる」ことと「条件を満たす情報を正確に調査できる」ことは別である。

SearchGuard は、その間に制御層を置くことで、

**検索回数、fetch回数、tool-loop、検索結果監査、fetch gate、current date/time、final-answer transition、異常診断**

を管理できるようになった。

そして 0.8.24 では、raw `<tool_call>` の発生状態を観測できるところまで到達した。

現段階では、さらにコードを複雑化するよりも、0.8.24をベースラインとして実測データを蓄積する方が合理的である。

SearchGuard の次の課題は「もっと賢く検索させること」ではない。

**どの層が検索品質を制限しているのかを、再現可能な実験で切り分けること**

である。
